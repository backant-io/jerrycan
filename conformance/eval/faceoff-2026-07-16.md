## Verdict

FastAPI won on agent efficiency and reliability: 2.2× cheaper, 2.6× faster, 5/5
verified, zero framework friction, zero false claims. But its green suites concealed
7 security footguns (salted-SHA-256 passwords, plaintext non-expiring tokens, hardcoded
JWT secret, client-forgeable health data, any-user-can-close-any-auction) — silent
production debt of exactly the class jerrycan's contract prevents: the jerrycan lane
shipped zero. The July 2026 fix batch (#27–#34) held completely: no agent hit the
tenancy trap, JWT guards worked, no identity-FK 422s.

Practical positioning today: jerrycan buys correctness-by-contract at ~2.2× token cost,
with jobs and realtime as its rough edges. Issues filed from this round: #47–#53.

## 2. Framework-bug verification (CONFIRMED / REFUTED with source evidence)

### FB-1 — CONFIRMED (framework-bug): entity-blind test seeding for multi-entity modules  *(J3)*
`crates/jerrycan/src/platform/testgen.rs:71-76` — `creator()` finds **only** the module-root `POST "/"`. `:181-204` — `seed` is always built from that root creator. `:252-258` — *any* 1-`{id}`-param endpoint reuses that same seed. So for a module owning Project (root `/`) **and** Task (`/tasks/{id}`), the generated `update_task`/`delete_task` probes seed a **Project** (id 1) then `PUT/DELETE /projects/tasks/1`, which correctly 404s (no Task id 1). J3's verbatim failure matches. **Severity: MEDIUM-HIGH** — emits false-red tests that look like the agent's bug; no documented escape (`probe:skip` is credential-framed, not seeding-framed). J3's classification is correct.

### FB-2 — CONFIRMED (framework-bug; agent under-classified as docs-gap): cron leader silently no-ops on SQLite  *(J4)*
- `crates/jerrycan/src/platform/jobsgen.rs:141` emits `Jobs::postgres(db)` **unconditionally** (no dialect branch).
- `crates/jerrycan-jobs/src/lib.rs:80-91` — `Jobs::postgres` always sets `pg_leader = Some(pg)`.
- Serve loop `crates/jerrycan-jobs/src/lib.rs:338-348` — `if let Some(pg) = &jobs.pg_leader { pg.cron_tick(...) } else { jobs.cron_tick_once(...) }`. With `pg_leader = Some`, it takes the Postgres path.
- `crates/jerrycan-jobs/src/postgres_store.rs:256-263` — `cron_tick` returns `Ok(0)` immediately when `backend() != Postgres`.
- Framework's own test names the behavior: `cron_tick_is_a_noop_on_non_postgres` (postgres_store.rs:921-930).
Net: on the env-mandated SQLite, a declared cron job compiles, passes `check`, and **never fires — no error, no log**. The working in-memory `cron_tick_once` (lib.rs:159) is only reached when `pg_leader = None`, which generated code never produces. **Severity: HIGH** — a silently-dead scheduler on the only supported dev DB. I reclassify from the agent's `docs-gap` to **framework-bug**. J4's spec-sanctioned fallback (admin endpoint) was the right move.

### FB-3 — CONFIRMED (framework-bug): no server-side broadcast publish API  *(J5)*
`crates/jerrycan-realtime/src/lib.rs:381-384` — `RealtimeHandle` (the dep handlers resolve) exposes only `pub(crate)` `hub`/`resolver`. `bus.rs:61,81`, `broadcast.rs:14,82` — every `publish`/`deliver_broadcast` is `pub(crate)`. The only `pub` broadcast surface is the builder `Realtime::broadcast(name, scope)` (lib.rs:115), which merely declares a **static** topic at design time. A REST handler in the generated app crate therefore **cannot publish** onto a broadcast topic — the canonical "row created via REST → live-push to subscribers" pattern has no first-class API on the SQLite-compatible primitive (Changes needs Postgres). J5's workaround (handler self-dials its own `/realtime` WS as a client to emit the publish frame) is real and confirmed. **Severity: HIGH** for realtime apps.

### FB-4 — CONFIRMED (docs-gap, high impact): enum out-of-range → 500, not 4xx  *(J2 + J3, hit independently)*
`crates/jerrycan-db/src/lib.rs:264-277` — `db_error` special-cases **only** `UniqueConstraintViolation` → 409; every other `DbErr` (incl. a CHECK-constraint violation from an out-of-enum value) → `JC0510`/500 (test confirms: lib.rs:331). The generated model carries **no** auto `Validate` impl for `values` fields, and `fixture_value` (testgen.rs:13-16) is enum-aware for the *happy* path only. Yet `docs/ai/00-designing.md:159-160` states a `string`+`values` field "becomes a TEXT column with a CHECK constraint **plus `Valid<T>` validation**" (repeated :574-575) — which reads as automatic 4xx rejection. It is not automatic: invalid enum input 500s unless the agent hand-writes an in-handler allow-list. Both J2 and J3 lost 3–5 min each discovering and hand-fixing this. **Severity: HIGH** (broadest blast radius — every app with a status enum; docs actively mislead).

### FB-5 — CONFIRMED (docs-gap): fixed `"test-value"` fixture vs hand-written `Valid` impl  *(J2, J4)*
`testgen.rs:13-26` — the happy-path fixture is enum-aware (`f.values.first()`) but blind to hand-written `Valid` impls; a plain `string` field always gets `"test-value"`. A spec-required format rule (valid email) rejects it, so the endpoint's own 2xx probe becomes un-greenable — the *same shape* as a credential gate but a different, undocumented cause. `probe:"skip"` (design.rs:308-345; documented 00-designing.md:198-201) suppresses it, but neither the docs nor SKILL connect `probe:skip`/the un-greenable exemption to the *validation-conflict* case — they name only login/webhook/api-key. This directly produced J4's mis-graded `complete`. **Severity: MEDIUM-HIGH.**

### FB-6 — PARTIALLY CONFIRMED (design-limitation; J4 overstated): no cross-module repo sharing
`crates/jerrycan/src/platform/lints.rs:195-218` — **JL0001** flags any route crate whose `lib.rs` exports more than `pub fn module()`; remedy text: "make it `pub(crate)`, move shared types to the shared crate, or expose via `module()`." So a sibling module's `model`/`repo` types are indeed unreachable from another route crate — J4's core observation holds. But "there is no supported way to share across modules **at all**" is overstated: the framework's intended channel is the `shared` crate (and for a foreign table, a narrow second SeaORM entity — exactly J4's workaround — is idiomatic). **Severity: MEDIUM** (real friction; requires editing a tool-owned `lib.rs`, which a regen would clobber).

- **J5 realtime round-trip + unauth reject**: proven in realtime.log independent of the ignored generated placeholder. Correct.

### REFUTED / corrected claims

## 4. Unguarded footgun catalog

Production-reviewer red flags. Every one is an **agent decision FastAPI left wide open** — the
kind a contract-driven framework (jerrycan) would make once, correctly, for the agent. None
failed a test or smoke step; the green scores are blind to all of them.

1. **F2 — passwords hashed with salted SHA-256** (`auth.py:11`, `hashlib.sha256(salt+pw)`). A
   fast general-purpose hash, no work factor → GPU-crackable at scale. Chosen explicitly to
   "avoid a dependency." (F3 used bcrypt, F5 pbkdf2_sha256 — so the *same task* got 3 different
   password stances across agents, one of them unsafe.)
2. **F2 — bearer tokens stored PLAINTEXT** as the PK of a `tokens` table (`models.py`), **never
   expire, never pruned** (`create_token` only inserts). DB read = full account takeover; table
   grows unbounded, one row per login forever.
3. **F3 — bearer token stored PLAINTEXT on the `User` row** (`models.py:38`), **no expiry**,
   one-token-per-user (each login overwrites → silently kills the user's other sessions). DB read
   = takeover.
4. **F5 — hardcoded JWT signing secret in source** (`auth.py:13`, `"liveauction-eval-secret-key"`),
   HS256, and being stateless JWT there is **no revocation** — a logged-out/closed session's token
   stays valid for the full 60 min. Self-flagged as "eval-only," but nothing in the framework
   forces the secret out of source.
5. **F4 — check timestamps are fully client-forgeable** on an **unauthenticated** `POST
   /checks` endpoint. The same `created_at` field that makes the stale-transition testable also
   lets any caller spoof a monitor's health (inject a future timestamp → forever "healthy").
   Health state is attacker-controlled.
6. **F5 — `POST /auctions/{id}/close` has no ownership check** (main.py:83) — *any* authenticated
   user can close *anyone's* auction. Logged as a "guess," but it's a broken-authorization hole.
7. **Cross-cutting — no password policy** (F2 `min_length=1`, F3/F5 none) and **ad-hoc
   duplicate-account / conflict codes** decided per agent (dup-email 400×3; dup-title 409). Every
   auth primitive was re-invented independently, with no framework floor.

Plus F4's `POST /admin/sweep` is an **unauthenticated state-mutating admin endpoint** (spec said
"no auth," so in-bounds, but it would be a footgun in any real deployment).

## 6. Top-5 observations — FastAPI's agent-experience vs a contract-driven framework

**Strengths**

1. **Declarative validation is nearly free and uniformly correct.** Pydantic
   `Field(gt=0/ge/le/max_length)` + str-Enums + `field_validator` produced *every* 422 the specs
   demanded with zero custom code, and it was right in all 5 apps (verified live: -5→422,
   ftp://x→422, bad currency→422, bid<min→422, servings=0→422). This is FastAPI's clearest win —
   an agent gets input-contract enforcement for the price of a type annotation.

2. **Almost no framework friction on well-trodden shapes.** Five cold-start agents, **zero
   framework bugs, zero time-costing docs-gaps.** Idiomatic project structure
   (models/schemas/deps/main, `get_db` dependency, `TestClient`) reproduced from training alone.
   For CRUD + auth + even WebSocket broadcast, FastAPI's surface is stable enough that a
   from-scratch agent lands on the conventional layout unaided.

3. **Hand-written tenancy isolation was clean *when the agent knew the rule.*** The 404-not-403
   cross-user requirement (F2 `_get_owned_wallet`, F3 `_get_ticket_or_404`) was implemented
   correctly by every agent because they wrote the filter explicitly. FastAPI didn't help, but it
   didn't get in the way.

**Weaknesses**

4. **Every unspecified detail becomes an unguarded, per-agent judgment call.** 32 documented
   guesses + 7 security footguns. FastAPI decides *nothing* for the agent about password hashing,
   token storage, token expiry, JWT secret handling, authorization ownership, or error codes — so
   each agent re-invents (and, in ≥4 cases, mis-invents) security primitives. The identical
   "store hashed" requirement yielded SHA-256 (unsafe), bcrypt, and pbkdf2 across three agents. A
   contract-driven framework that bakes these in would erase all 7 footguns and most of the 32
   guesses *by construction* — this is the central divergence: **FastAPI gives uniform correctness
   on the validation it models, and uniform divergence on the security it doesn't.**

5. **The dangerous defaults are silent, and "complete" cannot see them.** Salted-SHA-256
   passwords, plaintext non-expiring tokens, a hardcoded JWT secret, forgeable health timestamps,
   and an ownerless close endpoint **all passed tests, smoke, and earned `status:"complete"`.**
   The eval's success criteria — the thing that produced five "perfect scores" — is structurally
   incapable of detecting production-unsafety. That blind spot is exactly the gap a
   contract/verification-driven framework closes: it moves these decisions from "invisible agent
   guess graded green" to "framework guarantee." The most important audit finding in this lane is
   not a false claim; it's that **truthful perfect scores still shipped 7 footguns.**

*(Bonus — the one place the framework bit a competent agent: WebSocket + dependency injection.
`Depends()`/`dependency_overrides` don't extend to a generator you invoke by hand inside an
`@app.websocket` handler, and it fails **silently** — the test's rows simply "don't exist" from
the socket's DB session, surfacing as an opaque 1008, not an error. F5 lost 4 min here; it's the
sharpest undocumented edge in the lane.)*
