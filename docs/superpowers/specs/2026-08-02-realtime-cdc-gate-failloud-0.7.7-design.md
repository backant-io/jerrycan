## Part A (#228) — the Replication arm fails loud / degrades instead of looping into a dead feed
In `start_change_source` (`lib.rs:659-685`) + `run_supervised`/`ensure_replication` (`replication.rs:321-345`): distinguish NEVER-CONNECTED-ONCE (permanent-ish) from a DROP-AFTER-CONNECT (transient, keep retrying). On the FIRST `ensure_replication`/`stream_once` failure (before any successful stream), do NOT loop silently — instead, in preference order:
1. **Preferred — degrade to the trigger source:** attempt `start_change_source`'s trigger path (the same `ensure_triggers` + `TriggerAdapter` the trigger branch uses). If triggers install, the app still gets changes (graceful degradation replication→trigger). If triggers ALSO fail the DDL (the #212 condition), then:
2. **Floor — mark unavailable:** `hub.changes_unavailable.store(true, Ordering::Relaxed)` (mirroring the #212 branch at `lib.rs:689`) so a `changes:` join is refused JC0530 instead of admitting a dead feed.
A drop AFTER a successful first connect stays transient (retry with backoff, as today). Pick the simplest implementation that achieves: a permanently-mis-provisioned replication PG never presents a silently-dead `changes:` feed. If the replication→trigger fallback is too invasive for this release, the floor (mark unavailable on first-connect failure) is acceptable alone — state which you did.
