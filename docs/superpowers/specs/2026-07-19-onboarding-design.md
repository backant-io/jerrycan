# jerrycan onboarding, README & code-quality — design spec

**Date:** 2026-07-19 · **Status:** awaiting review

## 1. Problem

Getting from "heard about jerrycan" to "agent is building my backend" today requires:
a Rust toolchain, `cargo install jerrycan` (minutes of compile), manual MCP wiring,
and — for the guided flow — cloning this repo to get the `jerrycan-backend` skill.
The skill, the framework's biggest DX asset, has **no distribution mechanism at all**.
The README quickstart is written for people already on the repo page, still says
0.2.0, and has no single action to hand to an agent.

**Goal:** one pasteable line that works in any AI agent, which installs the
framework + the guided skill, then interactively scopes what to build
(explore current project / start from scratch / migrate from Supabase),
collects requirements, plans, and implements the backend. Plus: README that
leads with that line, and a prioritized burn-down of the open quality issues.

## 2. Assumptions & locked decisions

- **"Any AI agent"** = an agent that can fetch a URL and run shell commands
  (Claude Code, Cursor, Codex CLI, Windsurf, …). The runbook must not depend on
  Claude-specific features; Claude Code gets the native skill as a bonus.
- **Interactivity lives in the agent, not the script.** `install.sh` is
  non-interactive and idempotent; the *runbook/skill* instructs the agent to ask
  the user the scoping questions (matches the existing skill's golden rule 1).
- **No Rust toolchain required.** Primary audience includes zero-knowledge
  vibecoders; the installer ships prebuilt binaries, `cargo install` is the fallback.
- **"Migrate from other framework"**: v1 supports **Supabase only** (the path that
  exists: `jerrycan migrate --from supabase`). Other sources are named as a scope
  wall in the flow, not silently promised. Generic-Postgres import is a follow-up.
- **Never overwrite user config.** Skill/MCP install is create-if-absent or
  content-hash-compare-then-update; agent configs are appended to, never replaced.

## 3. Approaches considered

**A — Prompt-as-URL + prebuilt binaries + CLI-embedded runbook (recommended).**
A hosted agent-readable runbook (`jerrycan.cc/start`) drives install + guided
flow; `install.sh` (generated by cargo-dist) installs binaries + skills; the
guided flow is also embedded in the CLI (`jerrycan onboard`) so it is versioned,
offline, and agent-agnostic — same twin-sync discipline as `jerrycan docs`.
*Trade-off:* needs a release pipeline for binaries (one-time cost).

**B — Skill/MCP-only distribution, keep `cargo install`.**
Cheapest, but keeps the Rust-toolchain wall — kills the vibecoder path. Rejected.

**C — Separate installer wizard binary (à la backant-wizard, via npx).**
A second artifact to version and maintain, and npx assumes Node. The shell
script + cargo-dist covers the same ground with less surface. Rejected.

## 4. Design (approach A)

### 4.1 Prebuilt binaries (the pipe)

Release workflow (cargo-dist or an equivalent GH Actions matrix) building
`jerrycan` for macOS arm64/x64, Linux x64/arm64 (musl), Windows x64 on tag push;
artifacts + checksums on GitHub Releases. Stays compatible with the existing
3-tier CI and the publish gate; the release workflow runs *after* the
crates.io publish gate, never instead of it.

### 4.2 `install.sh` — one script, three jobs

Hosted at `https://jerrycan.cc/install.sh` (redirect/alias: `/install`), also in
repo under `scripts/`. Non-interactive, idempotent, `set -euo pipefail`:

1. **Binary install:** detect OS/arch → download release binary → verify
   checksum → install to `~/.jerrycan/bin` (PATH hint printed, shell rc line
   appended only with an explicit marker comment, never duplicated).
   Fallback: `cargo install jerrycan` if platform unmatched and cargo exists.
2. **Skill install:** write the `jerrycan-backend` skill to
   `~/.claude/skills/jerrycan-backend/` (create-or-update by content compare).
   The skill files ship inside the release artifact so script and skill
   versions can never diverge (`jerrycan onboard --emit-skill` writes them; the
   script just calls it).
3. **MCP wiring (best-effort, detect-only):** if `claude` CLI exists →
   `claude mcp add jerrycan -- jerrycan mcp` (skip if already present); else
   print the stdio JSON snippet for Cursor/other clients. Never edits foreign
   config files.

Exit summary is machine-readable (`--json` flag) so agents can verify success.

### 4.3 The pasteable line + hosted runbook

The one-liner (README hero, landing page, llms.txt):

> **Paste into any AI agent:**
> `Fetch https://jerrycan.cc/start and follow it to set up jerrycan and build my backend.`

`/start` serves markdown (agent-readable, human-tolerable) containing:

1. Run `curl -fsSL https://jerrycan.cc/install.sh | sh` and verify with
   `jerrycan --version`.
2. Run `jerrycan onboard` and follow its output exactly.

That's the whole file — thin by design; all process content lives versioned in
the CLI, so `/start` never rots.

### 4.4 `jerrycan onboard` — the guided flow, embedded

New CLI subcommand that prints the guided-process runbook (the SKILL.md
content, adapted to be agent-neutral), twin-synced the same way as
`docs/ai` ↔ `embedded/ai` (extend `embedded_sync`). First instruction to the
agent: **ask the user which entry path applies** —

- **(a) Explore current project** — existing Phase 1 frontend-analysis flow.
- **(b) Start from scratch** — existing Phase 1 elicitation flow.
- **(c) Migrate from Supabase** — new phase: produce the export
  (docs page `migrate-supabase`), run `jerrycan migrate --from supabase`,
  walk the gap-report with the user, then rejoin Phase 5 (implement) →
  Phase 6 (verify). "Other framework" → scope wall named honestly, offer (b)
  with the old system as reference material.

Then proceed through the existing Phases 1–7 (elicit → scope → design.json →
scaffold → implement → check → hand off). Deliverable includes updating
`docs/SKILL.md` + `.claude/skills/jerrycan-backend/SKILL.md` twins with the
three-way branching and the migration phase.

### 4.5 README overhaul

- **Hero:** the pasteable one-liner first; `cargo install` demoted to
  "For humans / from source".
- **Fix staleness:** version callout says 0.2.0 (workspace is 0.5.0 — pull from
  a single source or drop the number), rust badge says 1.88+ (policy is
  1.97 MSRV), crate layout lists 9 of 11 crates (missing realtime, storage).
- **Structure:** hero → 30-second agent onboarding → what you get → proof
  ("Does it actually work?" stays — it's the differentiator) → human quickstart
  → scope honesty → roadmap → sponsors.
- Same one-liner propagated to jerrycan.cc landing + llms.txt.
  **Conflict surfaced (Rule 7):** `docs/marketing/jerrycan-cc-design-handoff.md`
  locks CTA copy to "GitHub + `cargo install`" — supersede it with the
  one-liner and note the change in that doc.

### 4.6 Onboarding eval (measured, not asserted)

A manual heavy-tier check mirroring the conformance ethos: clean container
without Rust → run `install.sh` → `jerrycan onboard` runbook parsed → scaffold
a reference design → `jerrycan check` green. Wired as a job in `heavy.yml`,
not per-PR.

**0.6.0 = the onboarding release** (rows 1–6).

## 6. Success criteria

- Clean machine, no Rust, any capable agent + the one-liner → running, tested
  backend from a from-scratch design in a single session; same for the
  Supabase path against a reference export.
- `install.sh` run twice = no-op second time; never clobbers existing config.
- README contains zero stale version/toolchain/crate claims.
- Onboarding eval green in heavy.yml.
- #102 closed before the one-liner is promoted anywhere public.

## 7. Open questions (for Pavel)

1. **Where does jerrycan.cc deploy from?** No site repo found under backant-io
   (only `jerrycan-design`, the design system). Hosting `/install.sh` + `/start`
   needs that repo or a Cloudflare Worker route — which?
2. **cargo-dist vs hand-rolled matrix?** cargo-dist generates installer +
   updater for free but adds a tool to the release path. Default: cargo-dist
   unless you veto.
3. **Skill install scope:** user-level `~/.claude/skills` (works across
   projects) vs per-project `.claude/skills`. Default: user-level, with the
   onboard runbook offering to copy per-project.
4. **Windows:** binary yes, but `install.sh` is sh-only. Ship `install.ps1` in
   v1 or defer? Default: defer, document WSL.

## 8. Out of scope (this cycle)

- Migration sources beyond Supabase (generic-Postgres import is the named next).
- GUI/TUI installer; auto-updates beyond what cargo-dist provides.
- Landing-page visual redesign (copy/CTA changes only).
