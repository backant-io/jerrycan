# Response-hidden fields: `write_only` (0.6.8) — #112

**Date:** 2026-07-26
**Status:** Approved design, pre-implementation
**Issues:** #112 (HIGH — generated `Model`s serialize every column, so secret columns like `password_hash` leak in API responses by default; the docs' own accounts-api example and the Supabase migrator both ship `password_hash` in responses).
**Ships as:** 0.6.8 — a security-default feature. Additive `write_only` field flag; whole feature lives in the `jerrycan` CLI crate's codegen (no runtime-crate change). Byte-identical for designs with no `write_only` field AND no `password_hash` column; designs with a hidden-secret column change (their responses stop leaking the secret — the intended fix).

## Problem
Handlers return the entity `Model` DIRECTLY as the response body (`return_type`, genroute.rs:45-57 → `Json<{Entity}>`), and the `Model` derives `Serialize` over every column (`model_rs` genroute.rs:653-682, `model_rs_db` :923-1023). There is no response DTO. So any secret column is serialized in every response. **Live leaks confirmed:** the migrator emits `User{id,email,password_hash}` with `register`/`login` returning `entity:User` (`migrate/authmap.rs:40-96`) → every migrated app leaks the hash; the docs example (`docs/ai/20-designing-examples.md:236`) leaks it; the `tenant-is-identity` fixture carries it.

## Design

### A. Contract: `write_only` on the field
Add `write_only: bool` to `Field` (design.rs:169), mirroring `unique`/`index`: `#[serde(default, skip_serializing_if = "std::ops::Not::not")] pub write_only: bool` + a `// #112` doc comment. (`Field` has no `Default` derive — update the ~6 `Field { .. }` struct literals: `migrate/authmap.rs`, `migrate/entities.rs`, and the test builders in questions.rs/genroute.rs.) Mirror in `docs/contracts/design-schema.json` (pinned by `tests/contracts.rs`).

### B. Classifier + secure-by-default
Add `Design::field_is_write_only(f: &Field) -> bool` = `f.write_only || f.name.eq_ignore_ascii_case("password_hash")`. The literal-`password_hash` auto-classification is the **secure-by-default** for the one unambiguous secret name (fail-CLOSED: silently *hiding* a password hash is the safe direction; a hash should never be in a response). The broad name heuristic (`*_hash`/`token`/`secret`/`api_key`) is deliberately NOT included — too fragile (a `share_token`/`oauth_token` may legitimately be returned). Documented.

### C. Emission — hide on output, keep on input (the load-bearing distinction)
For a `field_is_write_only` field, emit **`#[serde(skip_serializing)]`** on the Model field at BOTH sites: `model_rs` (genroute.rs:664-675) and `model_rs_db` (genroute.rs:957-975, both the required and optional branches — inject alongside the existing keyword/constraint attrs). **Use `skip_serializing`, NEVER `skip`:** the Model is ALSO the input type in the no-DTO path (`Json<{Entity}>` body, genroute.rs:253-254) AND the SeaORM DB row (round-trips through serde), so `skip` (both directions) would drop the field from client input and break the DB row — a bug. `skip_serializing` hides output only; SeaORM still SELECTs the column so the handler still holds the value (e.g. for password verification). The request DTO `{Entity}Request` (genroute.rs:1070-1124) naturally retains the field (input unaffected — no change needed). `write_only` is orthogonal to who-SETS the value (v1: still client-settable input; server-computed secrets are a separate concern, #34).

### D. OpenAPI
In `field_schema(&Field)` (openapi.rs:7-34, the #80 site), emit `writeOnly: true` when `field_is_write_only`. The entity component is shared between the request-body-when-no-DTO and the response `$ref`; OpenAPI `writeOnly` (present in requests, omitted from responses) is semantically correct for both — the low-risk idiomatic choice (vs excluding the property). Request DTO schema (openapi.rs:219-251) keeps the field (input). Member-surface schemas are separate — unaffected.

### E. Validation — `JC0554` (next free; codes.rs)
Refuse an EXPLICIT `write_only: true` on the pk `id` field (mirror the `f.name == "id"` guard, questions.rs:742) — the id must be returned (the `id_echo` probe testgen.rs:715-722 and every cross-scope test key on `body["id"]`; hiding it breaks the generated suite by construction). `write_only` + `unique`/`index`/`values`/constraints is fine (DB/input concerns, orthogonal). Register JC0554 in codes.rs + `explain` + completeness test. (The `password_hash` auto-classification never applies to `id`, so no conflict.) Otherwise purely additive.

### F. Remediate the live leaks (part of this fix)
- **Migrator (`migrate/authmap.rs`):** the generated `User.password_hash` is now auto-hidden by the classifier; ADD an explicit `write_only: true` to that `Field` literal too (self-documenting; and so the emitted design.json shows the intent). Update the migrate goldens/e2e where the User Model / response schema legitimately change (password_hash now `skip_serializing` + `writeOnly`).
- **Docs example (`docs/ai/20-designing-examples.md:236` + the byte-identical embedded twin `crates/jerrycan/embedded/ai/20-designing-examples.md`):** add `"write_only": true` to the `password_hash` field and a sentence noting the response omits it. Edit BOTH copies identically (embedded_sync gate).
- **Fixture (`tests/fixtures/tenant-is-identity.design.json:14`):** its `password_hash` is now auto-hidden; update any golden that scaffolds it.

### G. Docs + conformance
- Document `write_only` (field semantics + the `password_hash` auto-default) in the field-reference doc (`docs/ai/00-designing.md` field list and/or `09-validation.md`) + embedded twin.
- Conformance e2e: a design with an explicit `write_only` field (e.g. an `api_token` on an entity) — scaffold → the generated `Model` has `#[serde(skip_serializing)]` on it → a response body does NOT contain the field, while a create request DOES accept it. (testgen asserts only `body["id"]` today, so no generated-suite breakage; optionally add a "response omits the write_only field" assertion — nice-to-have, not required for green.)

## Non-goals (deferred / documented)
- Separate request/response type generation (the `Model`-is-response design stays; `skip_serializing` is the mechanism). The broad secret-name auto-default heuristic (fragile). Field-level partial redaction / masking. Encryption-at-rest. Server-computed-secret injection (who sets `password_hash` — orthogonal, #34-adjacent). A generated response-omits assertion in testgen (v1.1 nicety).

## Success criteria
- A `write_only` field (and any `password_hash` column) is emitted with `#[serde(skip_serializing)]` on the Model → absent from every API response — while still accepted on create/update and stored. OpenAPI marks it `writeOnly`. The migrator no longer leaks `password_hash`; the docs example no longer leaks it.
- `write_only: true` on `id` → `JC0554`.
- Designs with no `write_only` field and no `password_hash` column are byte-identical; designs with a hidden secret change (responses stop leaking it — the fix). Heavy gate green; `cargo semver-checks` clean; published 0.6.8.
