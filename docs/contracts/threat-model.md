# jerrycan threat model

What jerrycan defends against, by what mechanism, and what it does not.
Every claim below names the path or code that implements it. Mechanisms that
do not exist yet are listed under *Residual risks*, not asserted here.

This document covers jerrycan 0.2.0. Contracts are not frozen until 1.0.

## 1. Scope & trust boundaries

```
client ──HTTP──> server (generated app) ──> database
                    ▲
                    │ generated by
              generation platform (`jerrycan` crate)
                    ▲
                    │ drives via design.json + MCP tools
                  agent (LLM)
```

Trust boundaries, from least to most trusted:

- **Client → server.** All HTTP input is untrusted. §2.
- **Agent → generation platform.** The agent authors `design.json` and the
  agent-owned source files. Both are untrusted input to the platform. §3, §4.
- **Generation platform → server.** The platform owns the tool-owned files of
  every generated crate and never executes agent code at generation time.
- **Server → database.** Single trusted connection; queries are
  parameterized through SeaORM / sqlx (`crates/jerrycan-db`).

The novel boundary is **agent → platform** (§4): the same model that writes the
app is treated as an adversary that may emit unsafe, leaky, or cross-tenant
code, and the platform's job is to make that mechanically detectable.

## 2. Network input (client → server)

Handled by the hyper serve engine and the core app, before any handler runs.

- **Per-route body cap**, default 1 MiB, applied to every method on the route
  (`crates/jerrycan-core/src/router.rs` `body_limit`; over-cap →
  `Error::payload_too_large` / **JC0413**, `crates/jerrycan-core/src/serve.rs`).
- **Transport timeouts**: header read 10s
  (`serve.rs` `HEADER_READ_TIMEOUT`), body read default 30s
  (`app.rs` `body_read_timeout` → **JC0408**), per-request handler budget
  default 30s (`app.rs` `handler_timeout` → **JC0503**).
- **Panic containment**: each request's dispatch runs in its own spawned task;
  a panic surfaces as a `JoinError` mapped to `Error::internal("handler
  panicked")` / **JC0500** (`crates/jerrycan-core/src/serve.rs`), so one
  request's panic never aborts the connection or the server.
- **Percent-decoding**: path segments are decoded after `/`-splitting;
  malformed encodings are rejected as `bad_request` / **JC0400**, never matched
  as literal text (`crates/jerrycan-core/src/router.rs` `decode_segment`,
  `crates/jerrycan-core/src/app.rs`).
- **Security headers** on by default — `x-content-type-options: nosniff`,
  `x-frame-options: DENY`, `referrer-policy: no-referrer`,
  `content-security-policy: default-src 'none'`, `cache-control: no-store`
  (`crates/jerrycan-core/src/app.rs` `apply_security_headers`).
- **No internal leakage in error bodies**: errors render as
  `{"code","message"}` (+ optional `details`) only
  (`crates/jerrycan-core/src/response.rs`). **JC0500** carries a generic
  message; **JC0510** is the constant `"database error"` with the underlying
  sqlx detail written to stderr for the operator, never to the client
  (`crates/jerrycan-db/src/lib.rs`).
- **Multipart parser surface** (`crates/jerrycan-core/src/multipart.rs`). The
  `multipart/form-data` framing is attacker-controlled, so the parser is a pure
  incremental state machine with no IO: it is unit-tested at every chunk
  straddle (`every_chunking_yields_identical_parts`) and fuzzed in isolation
  (`fuzz/fuzz_targets/multipart_parse.rs`, plus a stable-toolchain
  `fuzz_smoke` that runs in CI). Each unbounded direction has a cap before any
  need-more-data return: 8 KiB part headers (`MAX_PART_HEADER_BYTES`), 256 parts
  (`MAX_PARTS`), bounded boundary padding, and an 8 MiB per-part buffer cap for
  `bytes()`/`text()` (`DEFAULT_PART_CAP`) — all over-cap conditions are
  **JC0413**. The cumulative request `body_limit` still governs the whole body
  (via the `Limited` wrapper on the stream lane), and on a `stream_body()` route
  `body_read_timeout` is a per-frame deadline (**JC0408**), so neither a slow
  feeder nor an oversized body can be unbounded. Truncated framing is **JC0400**,
  never a hang (`truncated_input_is_malformed_not_a_hang`).
- **Slowloris-by-download** (`crates/jerrycan-core/src/app.rs`
  `write_stall_timeout`, default 30s). A client that opens a streaming download
  and then stops reading would otherwise pin a connection indefinitely; the
  socket-write stall budget drops it.
- **Stream truncation honesty** (`crates/jerrycan-core/src/response.rs`). A
  `StreamBody` that fails mid-stream — a producer `fail`/`Err` item, or a
  per-frame stall past `frame_timeout` (default 30s) — reaches hyper as a body
  ERROR, which aborts the chunked response. The client sees detectable
  truncation, never a cleanly-ended body that is silently incomplete
  (`channel_fail_surfaces_as_a_body_error_carrying_the_message`,
  `stream_body_frame_timeout_errors_the_body`).
- **Webhook verification** (`crates/jerrycan-auth/src/webhook.rs`). Signature
  checks (`verify_sha256_hex`/`verify_sha1_base64`) compute the HMAC over the
  EXACT request bytes (the `RawBody` extractor, not a re-serialized value) and
  compare in constant time (`hmac`'s `verify_slice`); malformed signatures fail
  verification rather than panicking. The Stripe recipe additionally bounds
  timestamp staleness against the injectable `Clock` to resist replay
  (docs/ai/10-auth.md).
- **CORS credentials safety** (`crates/jerrycan-core/src/cors.rs`,
  `crates/jerrycan-core/src/app.rs`). `CorsOrigins::any()` together with
  `allow_credentials(true)` is refused at **build time** (`App::build`), because a
  wildcard origin plus cookies is the classic cross-origin credential leak — the
  combination cannot be expressed. Echoed origins are validated fallibly when
  written back as a header value: bytes that don't form a valid `HeaderValue` are
  skipped, never panicked on. Every decorated response carries `Vary: Origin` so a
  shared cache can't serve one origin's allow-headers to another (cache
  poisoning). The preflight `204` deliberately omits the default security headers
  (notably `cache-control: no-store`, which would fight `Access-Control-Max-Age`
  and force a preflight on every request).
- **Rate-limit IP spoofing** (`crates/jerrycan-ratelimit/src/middleware.rs`). The
  IP partition tier keys on the RAW socket peer (`RequestCtx::peer_addr`) by
  default; `X-Forwarded-For` is honored ONLY when the operator opts in with
  `trust_forwarded_for(true)`, because that header is client-spoofable and would
  otherwise let an attacker forge a fresh partition key per request to evade the
  limit. The trusted-proxy assumption is the operator's: enable it only when a
  proxy you control rewrites the header. The raw peer is always present over a real
  socket, so the IP tier is not a production bypass — it degrades only in the
  no-peer test path (see fail-open below).
- **Rate-limit fail-open, hashing, and burst**
  (`crates/jerrycan-ratelimit/src/middleware.rs`,
  `crates/jerrycan-ratelimit/src/store.rs`). A request with NO identity (no
  api-key, no user-key, no peer) is NOT limited — fail-open is deliberate: a
  misconfigured limiter must not `500` all traffic. A STORE error, by contrast,
  fails CLOSED — it surfaces as **JC0500** rather than silently admitting the
  request, so a broken Redis is loud, not a hole. The api-key value is hashed
  (non-cryptographic, partitioning only) before it becomes a counter key; a rare
  hash collision makes two keys share one counter (stricter, never a bypass), and
  the raw key is never stored. The fixed window admits up to 2× the limit across a
  boundary (a client spending its quota at the end of one window and the start of
  the next) — a known fixed-window property, documented in docs/ai/06-middleware.md,
  not a defect.

## 3. Malicious `design.json`

`design.json` is validated before any code is generated
(`crates/jerrycan/src/platform/questions.rs::validate`); generation assumes a
validated design.

- **Schema validation** with `additionalProperties: false` throughout
  (`docs/contracts/design-schema.json`) — unknown keys are rejected.
- **Identifier patterns**: app/module names kebab-case
  (`^[a-z][a-z0-9-]*$`), job names snake-case (`^[a-z][a-z0-9_]*$`), entity
  names PascalCase (`is_kebab`/`is_snake`/`is_pascal` in `questions.rs`).
- **Rust-keyword rejection**: entity and field names that are Rust keywords are
  rejected, because generated `model.rs` would not compile
  (`RUST_KEYWORDS` in `questions.rs`).
- **Derived-fk collision check**: an explicit field whose name equals the
  column a `belongs_to` derives (`Design::fk_column`) is rejected
  (`questions.rs`).
- **Jobs cron shape**: a present job schedule must be cron-shaped, and job
  names must be unique (`questions.rs`; full cron parsing is deferred to the
  job engine).
- **Public-on-tenant-owned rejection**: an endpoint marked `public` whose repo
  entity is tenant-owned is rejected, because a public route bypasses the Tenant
  guard and would expose one tenant's rows to anyone (`questions.rs`).
- **Determinism**: the same `design.json` produces byte-identical output —
  enforced as a test invariant (`crates/jerrycan/tests/determinism.rs`), so
  agents can diff regenerations and the schema gate (§4) stays meaningful.

## 4. The agent as untrusted input

The defining threat class: the LLM that builds the app may emit unsafe or
boundary-violating code. Mitigations are mechanical.

- **Tool-owned vs agent-owned files.** Regeneration rewrites tool-owned files
  (`Cargo.toml`, `lib.rs`, subroute `mod.rs`, `app/src/main.rs`) and never
  clobbers agent-owned files (`handlers.rs`, `repo.rs`, `deps.rs`, `model.rs`,
  written create-once) — `crates/jerrycan/src/platform/genroute.rs`. Drift in a
  tool-owned file is flagged as **JL0003**.
- **`#![forbid(unsafe_code)]`** in every generated route crate's `lib.rs`
  (`genroute.rs`, `templates.rs`) and in the framework crates themselves
  (`jerrycan-core`, `jerrycan-auth`, `jerrycan-db`).
- **The JL lint family** (`crates/jerrycan/src/platform/lints.rs`):
  - **JL0001** — a route crate's `lib.rs` exports more than `module()`.
  - **JL0004** — an auth design leaves a mutating route unguarded (with public
    credential-issuing and signature-authenticated-webhook carve-outs).
  - **JL0006** — a tenant-owned handler calls an unscoped repo method, so it
    can read or delete another tenant's rows.
  - **JL0007** — agent-owned module code reaches outside the request boundary
    (`std::process`/`std::fs`/`std::net`, and the `tokio::` equivalents); a
    per-line `// jerrycan:allow JL0007` is the explicit opt-out.
- **The check gate** (`crates/jerrycan/src/platform/checkpipe.rs::run_all`):
  build → clippy (`-D warnings`) → cargo-audit → cargo-deny → tests → the JL
  lints → schema-contract freshness (**JC0520**, db mode). The first failing
  class stops the gate.
- **Generated isolation tests**: for a tenant-owned module the platform emits a
  cross-tenant test (user 1 must not reach user 2's rows) —
  `crates/jerrycan/src/platform/testgen.rs`.

## 5. Supply chain

- **Workspace gates in CI** (`.github/workflows/ci.yml`): `cargo fmt --check`,
  `cargo clippy -D warnings`, `cargo audit`, `cargo deny check`, the full test
  suite, bench build, conformance + eval, and a docs build with broken
  intra-doc links as errors; a separate `fuzz-build` job builds the fuzz
  targets.
- **Generated apps carry their own policies**: `deny.toml` (license allowlist,
  `yanked = "deny"`, unknown registry/git denied) and, in db mode,
  `.cargo/audit.toml` — written at scaffold time
  (`crates/jerrycan/src/platform/scaffold.rs`, `templates.rs`). Each ignored
  advisory is documented inline with its RUSTSEC id and rationale (e.g. the
  transitive `rsa` Marvin advisory under sqlx).
- **Dependency-justification policy**: every new dependency requires written
  justification in the spec that introduces it; audit/deny gates remain
  mandatory; dependency count is tracked per release
  (`docs/superpowers/specs/2026-06-11-jerrycan-v2-design.md` §non-negotiables).
- **MSRV** is declared (`rust-version = "1.88"`, root `Cargo.toml`) and tested
  in CI.

## 6. Residual risks / out of scope

Stated honestly; these are not defended today.

- **Agent logic bugs within the boundary.** The lints catch *classes* of
  escape (unsafe, leaks, cross-tenant, process/fs/net). A correctness bug in
  agent-authored handler logic that stays inside the boundary is the agent's
  and the reviewer's responsibility, not the framework's.
- **The unsafe-free guarantee does not extend to dependencies.**
  `forbid(unsafe_code)` covers jerrycan's own crates and the generated crates,
  not third-party crates in the tree (tokio, hyper, sqlx, …).
- **DoS beyond body caps.** Per-route body caps and transport timeouts bound a
  single request, but there is no connection-count cap or accept-loop
  back-pressure today — connection-flood back-pressure tuning is explicitly
  named for later (`docs/superpowers/specs/2026-06-11-jerrycan-v2-design.md`,
  "Named for later").
- **Crypto review is pending.** The hand-rolled session codec and JWT envelope
  (`crates/jerrycan-auth`) have not had independent external review; that
  review is a declared 1.0 gate before contracts freeze
  (`docs/superpowers/specs/2026-06-11-jerrycan-v2-design.md` §1.0 gates).
